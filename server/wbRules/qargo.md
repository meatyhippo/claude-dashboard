Qargo connector tools (call them by these names on the Qargo connector, qargo-mcp-prod or qargo-mcp-test; there are no wrapper tools). Every tool takes tenant_slug: pass it on every call (the ticket's sandbox by default, any other tenant when the question is about it, see DATA RULES). If a tool's schema is not loaded yet, load it with ToolSearch first.
- list_tenants {} · get_tenant_details {}
- internal_integrations_get_integration_instance_definition {integration_partner, instance_id?} returns the partner's config SCHEMA and actions (large). It is NOT the instance config.
- internal_integrations_run_integration_action {integration_partner, instance_id, action_label, parameters}. Read-only actions (the call still asks the person, since the same tool also runs writes): internal.provisioning.inspect with parameters {entity_type: integration_instance|order_import_master|task_master|planning_group|transport_service, mode: list|detail, entity_id?}: this is how you read what is configured on an instance (credentials.server, authentication_type, visibility_config.rules, routing). connection.list_routes {}. setup.validate {}.
- MAPPINGS: never read them with internal.provisioning.inspect (it only sees mappings tagged on the instance, so a mapping linked through a mapping group, e.g. dispatch_config or an order import, comes back empty). Read them tenant-wide: internal_datafetchershaper_list_transformation_mappings {group_id?, name?, limit?, offset?} (latest version per mapping; group_id and name filter the result, use group_id = the transformation_mapping_group_id the instance config points to) and internal_datafetchershaper_get_transformation_mapping {row_id} for the full transformation and output schema. Global ones: internal_datafetchershaper_list_global_transformation_mappings {name?, limit?} and internal_datafetchershaper_get_global_transformation_mapping {row_id}. An empty mapping result never means the mapping does not exist: check with these tools before saying so, and do not ask Qai about it.
- internal_integrations_list_routes {integration_partner, instance_id}
- internal_integrations_upsert_integration_instance {integration_instance:{row_id? (update), name, integration_partner_type, active:true (top level, otherwise the instance is created inactive), config:{generic_edi:{...}}}}. For a webhook visibility instance the config is config.generic_edi = {name, active:true, credentials:{server_type:"WEBHOOK", server:<url>, http_method:"POST", authentication_type:"UNAUTHENTICATED"|"BEARER"|"HEADER"|"BASIC", api_token?}, enable_visibility:true, visibility_config:{rules:[{send_status, send_eta, send_document, send_acceptance, send_order_import, send_handling_unit, send_position, visibility_order_global_transformation_mapping_code:"qargo_order_visibility_event", visibility_order_parameters:{}}], enable_visibility_to_origin:false}, routing:{incoming:{api:[],edi:[],webhook:[],no_server:[]},outgoing:{pull:[],push:[],export:[]}}}. Copy the shape from an inspected instance, change only what the ticket needs.
- internal_integrations_simulate_webhook_upload {integration_partner, instance_id, route_code, payload, dry_run?} (needs an incoming webhook route; outbound-only instances have none, test those by changing an order and reading the partner endpoint).
- internal_list_config {config_type, filters?, limit?} · internal_read_config {config_type, row_id} · internal_write_config {config_type, payload}
- find_entity {query} (name or reference → type and UUID) · internal_fetch_entity {entity_type: order|shipment|company|location|resource|..., row_id}
- filter_entities {entity: order|trip, filter, size?, offset?}. filter must be a condition {field, op, value} or a group {and:[...]}; an empty {} is rejected. Example, orders of the last 7 days: {"field":"end_stop.date","op":"relative","value":{"unit":"day","from":-6,"to":0}}; by status: {"field":"status","op":"in","value":["TO_PLAN"]}.
- External API (to create or change orders, trips, companies when a test needs real TMS activity): the full External API reference (all 140 operations, every field with type, required flag and enum values) is on the connector: read it with the connector's external_api_discover {search} (finds operation ids) and external_api_schema {operation_id} (every field with type, required flag and enum values); never guess and never ask Qai for it. external_api_call_read {operation_id, path_params?, query_params?}; external_api_call_write {operation_id, path_params?, query_params?, body} (always external_api_schema first; each write asks the person). The External API has no operation to plan a trip or set stop statuses (trips are GET only, plus the trip-import and subco-status-update webhooks); say so instead of searching further.
internal.provisioning.inspect is scoped to the instance_id you pass: mode list only shows that instance. To read another instance (for example one you just created) pass its row_id as instance_id and entity_id. The row_ids of writes done in this ticket are in this chat's earlier tool results.
Read again freely when you need a full or fresh result: reads are cheap and never ask.
Large results (response_mode gcs_offload) come back as a storage link: turn it into a signed link with internal_download_storage_file {url} and download it with Bash (curl -sL "<link>" -o /tmp/x.json), then read the file. For API shapes use external_api_schema; for instance config use internal.provisioning.inspect. Only when a download fails, hand the work to Qai with ask_qai (say which mapping or payload and what to do with it).
MORE QARGO TOOLS. For any tool below, or any argument you are not sure of, load the tool's schema with ToolSearch first and follow it.
- Counting and finding fields: get_filter_schema {entity: order|trip, prefix?: [group,...]} lists the fields filter_entities and aggregate_entities accept (call it without prefix first, then with the groups you need; only use fields it lists). aggregate_entities {entity, filter, metrics:[{name, op: count|sum|avg|min|max|count_distinct, field?, filter?}], group_by?:[{field, limit?, interval?: day|week|month}], order_by?:{metric, direction}, timezone?} for counts and totals; filter_entities lists rows.
- The app's own read queries (data the External API and inspect do not expose): app_registered_query_list {} → app_registered_query_schema {name, path?} → app_registered_query_run {name, variables?, fields?: [dotted paths]}.
- App actions (what a user can do in the app, e.g. planning): app_actions_list {search?} → app_actions_schema {name, type?}; running one is a write: app_actions_run {name, input} (asks the person). Check here before saying the tenant cannot do something the External API lacks.
- Config: config_type is one of SERVICE_LEVEL, TIME_WINDOW, STOP_EXTRA, CARGO_EXTRA, PACKAGING_TYPE, PACKAGING_SIZE, TRANSPORT_SERVICE, TASK, TASK_OVERRIDE, ALIAS. internal_get_config_schema {config_type} (create and update schema, list filters, notes) before every internal_write_config; internal_validate_config {config_type, payload} checks a payload without writing; internal_get_tenant_config {} is the raw tenant config; internal_delete_config {config_type, row_id} (a write) removes or archives one object.
- Billing entities (Peppol / e-invoicing): internal_integrations_list_billing_entities {include_archived?}; internal_integrations_upsert_billing_entity (a write) {billing_entity:{row_id?, legal_name, code, vat_number, company_registration_number, payment_iban_code, payment_bic_code, billing_location}}.
- DataShaper mappings, the full loop: internal_datafetchershaper_list_model_definitions {} (model keys) → internal_datafetchershaper_get_transformation_schema {input_model_keys?: [..], output_model_key?} → internal_datafetchershaper_fetch_transformation_input_data {input_schema_inputs:[{input_model_key, source_type, row_ids:[uuid], include_flags?}]} (real rows to test with) → internal_datafetchershaper_transform_document {input_data (must hold a _meta key), transformation, transformation_input?, transformation_output?, output_format?} is a DRY RUN, nothing is saved: pass transformation_input and transformation_output exactly as fetched from the mapping. Saving is a write (it asks the person): internal_datafetchershaper_create_transformation_mapping {from_row_id, as_revision?, name?, transformation? (standalone) | transformation_overrides? (linked to a global), version_description?, context_url?} makes a DRAFT; internal_datafetchershaper_update_transformation_mapping {row_id, ...same fields} changes a DRAFT only. Omit-to-keep: pass a field only when you change it; never pass {} for transformation_input or transformation_output (it wipes the XSD / EDIFACT / CSV config). After the write ran, re-read the mapping and check transformation_input, transformation_output, meta_transformation and examples survived. Never change a global mapping.
- The connector's own guides: read_resource {uri} (list_resources {} lists them). docs://internal/datafetchershaper/overview (read FIRST before any mapping work), /changing-mappings (before a dry run or draft), /expressions (JSONata), /helper-functions, /pitfalls (a dry run errors or comes back empty), /input-parsing (CSV, XLSX), /order-import (ORDER_IMPORT / ORDER_IMPORT_V2), /exports (egress, webhooks, accounting); docs://filtering/finding-fields and docs://filtering/addon-filters (before filtering on service level, vehicle category, container type, time window, extra or incident ids).
- internal_download_storage_file {url} turns a payload link from a log (message_payload_url, https://storage.cloud.google.com/<bucket>/<path> or gs://) into a signed download link; download it with Bash (curl) and read it; if that fails, give the person the link.
- Integration actions: internal_integrations_get_integration_instance_definition lists every action label of the partner. Only the read-only ones named above are safe to run; any other label changes the tenant.
DISPATCH AND OUTBOUND DEBUGGING. Never say a trip, order or file was not sent before you checked these three sources:
- Dispatch input data: internal_datafetchershaper_fetch_transformation_input_data for RALLOC_DISPATCH often fails with "Cannot determine correct integration for dispatch". That error does NOT mean the dispatch failed. Read the order instead: external_api_call_read {operation_id:"get_order_details_v1_orders_order__order_id__get", path_params:{order_id:<order uuid>}}. It returns the same order shape as RALLOC_DISPATCH orders[], so paths map 1:1 ($.orders[0].<path>). Known paths: customer.name, name (order reference), container.container_scenario (IMPORT|EXPORT), container.container_type.{name, code, container_iso_code}, container.container_number, custom_fields, stops[].location.{name, postal_code}, stops[].time_window.start_time ("HH:mm:ss", trim to HH:mm with $substring(x,0,5)). Find the order uuid with find_entity {query:"<order ref>"}. For a field path you cannot find, read a global mapping that uses it: internal_datafetchershaper_list_global_transformation_mappings {name:"data2track"} then get_global_transformation_mapping (it reads container_scenario and container_type from the same input). Then dry-run with internal_datafetchershaper_transform_document, input_data {_meta:{}, orders:[<the order>], ...trip fields}.
- Egress log (what really went out, and why it failed): the Lightdash connector's run_metric_query on project d4d21d1b-488b-4ff0-8a1e-a621c498c932, explore ingress_egress_logging. Load run_metric_query's schema first, then Lightdash grep_fields {projectUuid, search:"ingress_egress_logging"} for the exact field ids. Dimensions: tenant_id (the tenant uuid from get_tenant_details), instance_name, action (RALLOC_DISPATCH for trip dispatch), event_type (START, EGRESS, SUCCESS, FAILURE), message_location (file name or URL it went to), reason (the error), message_timestamp, gcp_log_url, message_payload_url. Always filter on tenant_id and on log_timestamp (partition, last 7 days) or the query scans everything; sort on message_timestamp descending. A FAILURE row's reason is the answer; message_payload_url goes through internal_download_storage_file to read the exact file sent. Poll with get_query_result when the query is still running.
- Files on the partner SFTP: internal_integrations_run_integration_action {integration_partner, instance_id, action_label:"connection.list_files", parameters:{path:"<folder>"}} lists the files (the outbound folder is the instance's from_qargo_dir, see internal.provisioning.inspect); action_label "connection.read_raw" with parameters {path:"<folder>/<file>"} reads one file. If the connector rejects the parameters, read the action's schema in internal_integrations_get_integration_instance_definition (pick the action) and retry once.
Order of checks for "why was nothing sent": (1) egress log for the tenant and action, (2) SFTP listing, (3) the dispatch task and resource config. Only then ask Qai.
